# 01 · 发现：怎么定位到"序列号校验"

> 这一篇讲方法，不只讲结论。同样的思路可以迁移到别的车型、别的校验机制上。

---

## 1. 起点：两个看起来矛盾的现象

| 现象 | 直觉解释 | 实际原因 |
|---|---|---|
| 从车机应用商店下载的 APK，能正常安装 | "商店有特权" | 签名序列号与系统一致 |
| 自己用 Android Studio / apksigner 签名的 APK，装不上 | "缺白名单" | 同一个原因 |
| 把包名改成一个系统应用的包名，仍然装不上 | "白名单不是看包名" | 安装门根本不看包名 |

第三个现象是关键的反证：**如果安装门看包名，改包名应该有效；既然无效，说明它看的是别的东西。**

---

## 2. 第一步：排除"包名白名单"假设

做法：

1. 找一个已知能在车上安装的第三方 APK；
2. 记录它的包名；
3. 把自己的测试 APK 改成同样的包名、用同样的签名方式重签；
4. 再装一次。

结果：**仍然装不上**。

结论：安装门与包名无关。包名只影响"能不能卸"（卸载门）。

---

## 3. 第二步：对比两个能装的 APK

从车机应用商店下载两个不同来源的 APK（例如两个不同的官方应用），分别看签名信息：

```bash
keytool -printcert -jarfile app1.apk
keytool -printcert -jarfile app2.apk
```

观察结果（本车实测）：

| 字段 | app1 | app2 | 是否相同 |
|---|---|---|---|
| Serial number | `<TARGET_SERIAL>` | `<TARGET_SERIAL>` | ✅ 相同 |
| Owner / Issuer | 相同 | 相同 | ✅ |
| SHA-256 指纹 | `...` | `...` | ❌ 不同 |
| 公钥 | 不同 | 不同 | ❌ 不同 |

**这是决定性的证据**：

- 两个 APK 的公钥不同、指纹不同，却都能装；
- 它们唯一的共同点是**证书序列号**；
- 所以校验的是序列号，不是公钥、不是指纹、不是 DN。

> 如果只看"能装"这一个现象，可能会误以为是"应用商店有特权"。
> 对比两个样本，才能把变量收敛到序列号。

---

## 4. 第三步：找到校验代码

有了"校验序列号"的假设，接下来是定位实现。

### 4.1 从哪里下手

车机是 Android 9，签名校验通常发生在两个位置：

1. `PackageManagerService` / `PackageInstaller`（安装流程）；
2. 厂商自己加的 `CertificateManager`（常见于 `ext.jar`、`boot-ext.jar`、系统服务）。

本车的线索：

- 应用商店 APK 里引用了 `com.vecentek.security.CertificateManager`；
- `/system/framework/ext.jar` 里能找到这个类。

### 4.2 反编译

```bash
# 从车机拉取（需要 adb 或 root，视车机策略）
adb pull /system/framework/ext.jar

# jadx 反编译
jadx -d out_ext ext.jar

# 搜索关键方法
grep -rn "isCheckAuth\|CertificateManager\|getCertnum" out_ext/
```

### 4.3 读到的逻辑（简化）

```java
public boolean isCheckAuth(String packageName) {
    // 硬编码放行
    if (packageName.equals("com.keanbin.pinyinime")) return true;

    // 取 com.android.settings 的证书序列号
    if (getCertnums() == null) getCertnumbyself();

    PackageInfo pi = pm.getPackageInfo(packageName, GET_SIGNATURES);
    // 取目标应用的证书序列号，与 Settings 的比较
    return serialOf(pi).equalsIgnoreCase(settingsSerial);
}
```

关键结论：

- 比较对象是 **`com.android.settings` 的签名证书序列号**；
- 只比序列号，没有比公钥、指纹或 DN；
- 有一个硬编码白名单（`com.keanbin.pinyinime`），与本话题无关。

---

## 5. 第四步：实车验证

假设成立后，用最小实验验证：

1. 生成一张自签证书，**把序列号设成从官方 APK 提取的值**；
2. 用它给测试 APK 签名；
3. 安装。

结果：**安装成功**。

这一步同时排除了"应用商店特权""系统分区""UID"等其他解释——测试 APK 没有这些条件，
唯一改变的是证书序列号。

---

## 6. 第五步：意外发现——卸载门

装上去之后，新问题出现了：**设置里没有卸载按钮，`pm uninstall` 也失败**。

报错：

```
Failure [<pkg> is auth app, not allow delete!]
```

顺着这条线索继续反编译 `services.jar`，在
`PackageManagerService.deletePackageVersioned()` 里找到了卸载时的校验：

```java
WhiteListHelper helper = new WhiteListHelper();
boolean isWhite = helper.checkWhiteList(context, packageName);
if (!isWhite) {
    if (cert.isCheckAuth(packageName)) {
        // 签名匹配 Settings → 视为"授权应用" → 拒绝删除
        observer.onPackageDeleted(packageName, -7, pkg + " is auth app, not allow delete!");
        return;
    }
}
```

两件反直觉的事：

1. **白名单是"允许卸载的例外名单"**，不是"允许安装的名单"；
2. **签名匹配 Settings 反而会导致卸不掉**——因为系统把它当成"自己人"保护起来了。

这也解释了为什么"改包名"对卸载没用：白名单是服务器签名控制的包名列表，
改包名只会让你从一个"不在名单里"的包名，换到另一个"不在名单里"的包名。

---

## 7. 方法论总结

这套发现流程可以复用：

| 步骤 | 动作 | 目的 |
|---|---|---|
| 1 | 找两个"能成功"的样本 | 确定成功的共同条件 |
| 2 | 逐项对比它们的证书/配置 | 缩小变量范围 |
| 3 | 构造"只改变一个变量"的反例 | 排除其他解释 |
| 4 | 反编译定位实现 | 从现象到代码 |
| 5 | 最小实验验证 | 证明因果关系 |
| 6 | 顺着新现象继续挖 | 发现第二、第三道门 |

核心原则：

> **不要从"别人说的方法"出发，从"能成功的样本"出发。
> 对比两个成功样本，比读十篇教程更有用。**
