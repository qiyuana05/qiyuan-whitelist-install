# 00 · 背景：两道门

> 车机上跟"安装、卸载"相关的是两套独立的机制。把它们混在一起，是大多数教程失败、
> 以及"我明明签名了为什么还是卸不掉"的根源。

---

## 1. 两道门一览

```
┌────────────────────────────────────────────────────────────────────┐
│ ① 安装门：签名证书序列号                                           │
│    APK 证书 serial == 系统 Settings 的证书 serial                   │
│    校验：CertificateManager.isCheckAuth()                          │
│    失败：PackageInstaller 拒绝安装                                 │
├────────────────────────────────────────────────────────────────────┤
│ ② 卸载门：包名白名单                                               │
│    包名在 /back_up/allow_uninstall/whitelist.json 的 white_list 里  │
│    校验：WhiteListHelper.checkWhiteList() + RSA 验签               │
│    失败：设置里没有卸载按钮，或 pm uninstall 返回 -7                │
└────────────────────────────────────────────────────────────────────┘
```

一句话记忆：

> **签对序列号才能装，包名在白名单里才能卸。**

两者互不替代：

- 签对了序列号，不代表能卸（卸载门看包名）；
- 包名在白名单里，不代表能装（安装门看序列号）。

## 3. 两道门为什么容易混淆

因为它们都会在"装完应用"之后表现出来：

| 现象 | 实际原因 | 属于哪道门 |
|---|---|---|
| `INSTALL_FAILED_VERIFICATION_FAILURE` | 签名序列号不对 | 安装门 |
| 装上了，但设置里没有卸载按钮 | 包名不在 white_list | 卸载门 |
| `pm uninstall` 报 `is auth app, not allow delete!` | 序列号匹配了 Settings，被当成"授权应用" | 卸载门（但由签名触发） |
| 覆盖安装报 `INSTALL_FAILED_UPDATE_INCOMPATIBLE` | 新包签名与已装版本不同 | 安装门（覆盖场景） |

注意第 3 行：**签对序列号会让应用被当成"授权应用"，反而更难卸载**。
这是很多人没预料到的副作用，详见 [02-原理](02-原理-两道门的校验逻辑.md)。
