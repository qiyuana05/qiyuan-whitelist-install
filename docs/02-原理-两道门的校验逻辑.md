# 02 · 原理：两道门的校验逻辑

> 安装门和卸载门是两套独立实现，绑在同一条删除/安装链路上，但判断依据完全不同。

---

## 1. 安装门：只比序列号

### 1.1 校验位置

```
PackageInstaller / 应用商店 / adb install
  → PackageManagerService 安装流程
    → CertificateManager.isCheckAuth(packageName)
      → 取目标 APK 签名证书的序列号
      → 与 com.android.settings 的证书序列号比较
```

### 1.2 简化后的判断

```java
boolean isCheckAuth(String pkg) {
    if (pkg.equals("com.keanbin.pinyinime")) return true;  // 硬编码放行，与话题无关
    if (settingsSerial == null) loadSettingsSerial();
    String target = serialOf(pkg);       // 取目标包证书序列号
    return target.equalsIgnoreCase(settingsSerial);
}
```

### 1.3 校验的字段

| 字段 | 是否校验 | 说明 |
|---|---|---|
| 证书序列号（serial number） | ✅ | 唯一硬指标 |
| 证书 DN（CN/OU/O/...） | ❌ | 自签任意 DN 都能过 |
| 证书 SHA-256 指纹 | ❌ | 公钥不同也能过 |
| 公钥 | ❌ | 不需要厂商私钥 |
| 证书有效期 | ❌ | 只要签名验证本身通过 |
| 包名 | ❌ | 安装门不看包名 |

### 1.4 为什么"只比序列号"能成立

从实现角度，序列号是最容易拿到的字段：

- `PackageInfo.signatures` 拿到证书字节；
- 解析 X.509 后直接读 `getSerialNumber()`；
- 不需要验证证书链、不需要联网、不需要维护公钥库。

而"验证公钥/指纹"需要厂商预置可信公钥，一旦更换证书就要发 OTA，
维护成本高。所以在很多车机/定制系统上，序列号成了事实上的信任锚点。

这在安全上是一个**设计缺陷**：序列号不是秘密，也不具备密码学绑定能力。
任何人只要知道目标序列号，就能生成一张同序列号的自签证书。

## 2. 卸载门：服务器签名的包名列表

### 2.1 数据从哪来

```
应用商店（AppStore）
  → 定期请求服务器接口（带公钥 ID）
    → 返回 { white_list: "pkg1,pkg2,...", sign: "RSA签名" }
      → 写入 /back_up/allow_uninstall/whitelist.json
```

文件结构：

```json
{
  "white_list": "pkg1,pkg2,pkg3,...",
  "sign": "<RSA signature>"
}
```

### 2.2 校验位置

```
pm uninstall / 设置里的卸载 / PackageInstaller
  → PackageManagerService.deletePackageVersioned()
    → WhiteListHelper.checkWhiteList(context, packageName)
      → 读 whitelist.json
      → 用 native 白盒库里的公钥做 SHA256withRSA 验签
      → 验签通过后，对 white_list 做逗号分割 + equalsIgnoreCase 精确匹配
```

关键点：

- 公钥不是从 `/back_up/.../publicKey.cert` 读的（那个字段存在但未被使用）；
- 公钥来自 native 白盒库（`libvecent_enc_fw.so` → `libse_bt.so`）；
- 验签失败、文件缺失、字段为空 → 返回 `false`，**不会放行**。

### 2.3 白名单是"允许卸载"，不是"允许安装"

这是最容易误解的一点：

- 它在**卸载**链路上被调用；
- 命中名单 → 允许卸载；
- 不命中 → 继续看签名是不是"授权应用"。

所以它**完全不影响安装**。安装门是另一套代码。

### 2.4 为什么改包名没用

因为：

1. 白名单是服务器签名保护的固定列表，你在本地改不了；
2. 改包名只是换了一个"不在列表里"的名字，结果仍然是"不命中"；
3. 即使你改成一个在列表里的包名，也只能获得"可卸载"资格，
   安装仍然要过序列号门。

## 3. 两道门叠加后的实际效果

| 你的签名 | 包名 | 能否安装 | 能否卸载 |
|---|---|---|---|
| 序列号 = 系统 | 不在白名单 | ✅ | ❌（被当成 auth app 保护） |
| 序列号 = 系统 | 在白名单 | ✅ | ✅ |
| 序列号 ≠ 系统 | 不在白名单 | ❌ | —（装不上） |
| 序列号 ≠ 系统 | 在白名单 | ❌ | —（装不上） |

注意第一行：**签对序列号会让你"能装但卸不掉"**。

这不是 bug，而是设计的副作用：

```java
if (!isWhite) {
    if (cert.isCheckAuth(pkg)) {
        // 签名匹配 Settings → 认为是系统自己人 → 拒绝删除
        return -7;
    }
}
```

系统把"和 Settings 同签名"视为"授权应用"，并主动阻止它被删除。

---

## 4. 安全性评价

这套机制的核心问题：

1. **信任锚是序列号，不是公钥**：序列号可公开获取、可复制，不具备密码学绑定；
2. **只校验一个字段**：DN、公钥、指纹都不看，等于放弃了证书体系的主要保障；
3. **白名单的签名保护是好的**，但安装门没有采用同样的强度；
4. **"auth app"保护逻辑**把签名一致性当成特权，反而让伪造签名者获得额外保护。

对厂商的建议：

- 改为校验证书公钥或完整证书链（预置可信证书）；
- 或使用 Android 的 `signature` 权限 / `apksigner` 的 v3 签名 + 轮转密钥；
- 白名单机制可以保留，但应与安装门使用同一套信任根；
- 不要把"签名匹配"直接等同为"不可卸载"。
